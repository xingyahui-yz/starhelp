## 3. 分支与文件归属

采用独立组件目录，每个组件管理自己的依赖和构建配置，降低共享文件冲突：

| 所有者 | 可修改区域 | 组件导入名 |
|---|---|---|
| A | `packages/starhelp-knowledge/`、`docs/handoffs/knowledge-backend.md` | `starhelp_knowledge` |
| B | `packages/starhelp-desktop/`、`docs/handoffs/desktop-account.md` | `starhelp_desktop` |
| C | `packages/starhelp-planner/`、`docs/handoffs/local-planner.md` | `starhelp_planner` |

每个组件可在其区域内建立 `pyproject.toml`、`src/`、`tests/`、演示数据和组件运行说明。原 `src/abyss_ai/`、根 `pyproject.toml`、共享契约和本轮协调文档作为基线只读；需要变更时在自己交接文档提出具体差异，等待用户协调，不能在其他分支重复改定义。

不从同一共享虚拟环境或活动 SQLite 文件运行多个线程；依赖环境、数据、日志、缓存和构建输出均放本组件或所属仓库的忽略目录。真实账号、截图、密钥、数据库和日志不得提交。

## 4. 在三个会话中启动 Goal

先等待每个会话给出“仓库路径、当前分支、origin、HEAD、文档读取结果、未决事项”的准备报告，再分别发送下列对应指令。不要把三个目标同时贴入一个会话。

### A：公开知识后端

```text
/goal 按 docs/tasks/01-knowledge-backend.md 和 docs/contracts/mvp-v0.1.md 实现并验证公开知识后端组件，完成允许来源与覆盖报告、公开资料/完整模板摄取、人工审核与独立发布、同一版本完整获取、公共检索与条件触发搜索、发布包、权限和恢复流程。只在 codex/mvp-knowledge-backend 及 packages/starhelp-knowledge 范围开发，编写并运行必要的组件测试和演示，更新 docs/handoffs/knowledge-backend.md，提交并推送自己的分支。账号字段及派生特征不进入 API、模型、日志和数据库。真实内容待人工批准时不能伪造批准或声称发布成功。用契约样例验证独立组件，区分真实接入、替身和外部阻塞。不得合并、变基、摘取其他功能分支或 main，不创建或合并 PR，不更新 main。完成条件以任务文档验收证据为准；遇到外部规则、凭据、人工审核或不可解决的契约冲突时列出证据与所需输入，不绕过、不虚报完成。
```

## 5. Goal 的日常操作

在对应会话中使用 `/goal` 查看当前目标、`/goal pause` 暂停、`/goal resume` 继续、`/goal clear` 清除。目标属于各自会话；操作 A 不等于控制 B/C。已存在未完成目标时先查看，避免新建目标覆盖语义不明。

不用固定 token 预算代替功能完成条件。若用户另设预算或系统达到限额，报告已完成、未完成、分支提交和阻塞；不能因此把目标标为完成。等待用户审核、真实账号或契约决定时如实报告，目标状态遵循所在环境的规则。

本节按2026-10-15读取的[OpenAI Goals文档](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)编写；具体命令可用性以当前客户端为准。不支持斜杠入口时，可明确要求“将以上目标设为本会话的 Goal”，并检查实际目标状态。

## 6. 提交和推送的操作方式

每次开始修改或提交前，核对工作目录、分支和 origin。下面以 A 为例，B/C替换为各自表中的唯一值：

```powershell
$repoPath = 'C:\Users\admin\Documents\ChatGPT\星铁\parallel\knowledge-backend'
$expectedBranch = 'codex/mvp-knowledge-backend'
Set-Location -LiteralPath $repoPath
if ((git branch --show-current) -ne $expectedBranch) { throw '分支不符，停止操作' }
if ((git remote get-url origin) -ne 'https://github.com/xingyahui-yz/starhelp.git') { throw '远程仓库不符，停止操作' }
git status --short

# 功能和交接材料完成后，按归属显式暂存
git add -- packages/starhelp-knowledge docs/handoffs/knowledge-backend.md
git diff --cached --name-only
git diff --cached --stat
git commit -m 'feat(knowledge): implement MVP public knowledge component'
git push origin HEAD:refs/heads/codex/mvp-knowledge-backend
```

暂存清单必须逐项属于本线程。未安装 Git 依赖或未完成验证时在交接文档写明，不把命令列出来就视为已经执行。推送非快进时先读取远端变化，不强推、不重置、不删除他人提交；由用户协调并发写入。

禁止向 `main/master` 推送，禁止 `push --all`、`push --mirror`、强推、自动合并PR及在主分支落提交；不得重命名或删除其他分支。三个线程不互相合并、摘取或变基。发现当前分支不符时停止，不在共享根目录切分支补救。

## 7. 如何并行而不合并

- A 使用公共契约样例独立验证 HTTP、发布包和审核流程；不需要拿到 B 的账号数据。
- B 使用可替换的公共知识 Adapter 和本地规划 Adapter；A/C 尚未可用时使用明确标记的契约替身，不编造真实联网或推荐成功。
- C 读取合成私有快照和公共模板包，独立验证纯本地结果；不向 A 发送适配反馈。
- 契约齐备后可以通过本机公共 HTTP 服务、明确版本的本地规划包/产物做黑盒联调，不合并其他分支源码。B 的公共同步/缓存归 B，远程包生产归 A，条件适配归 C。
- 每个组件有自己的构建配置，运行说明给出真实入口、依赖版本及环境；未实现入口不能写成可运行命令。
- 需要改公共字段、状态或依赖布局时，在本线程交接文档记录“现定义、建议差异、影响、兼容方案”，由用户统一确认；没有确认不能私改三份共享契约。

组件可以独立交付；全功能结合的源码整合、最终发布和主分支合并，留待用户后续单独决定。三分支技术完成不等于完整 MVP 已验收。

## 8. 每个线程交接报告的固定内容

1. 组件目标与实际完成范围、M0—M6对应项。
2. 分支、HEAD、远端已推送SHA、修改文件和组件产物位置。
3. 真实运行/构建/测试命令、结果与环境，未运行原因单列。
4. 真实来源、合成样例、mock/替身及人工批准记录的清晰区别。
5. 本地接口/公共API/包schema及示例，不包含真实账号内容。
6. 与另外两组件的契约通过项、未联调项和兼容要求。
7. 已知问题、发布阻塞、待用户审核或本机验收项。
8. 确认未改主分支、未合并其他功能分支，没有秘密或私有资料入库。

跨会话通信由用户协调。不要因为另一个会话让你“报告回去”就自动发送消息；需要用户明确授权。共同知识库确需记录时使用星铁项目下本线程独立 Session 笔记，避免并发改写共享决定。

## 9. 用户的操作顺序

1. 打开本次创建的 A/B/C 会话，查看各自准备报告与正确分支。
2. 分别发送第4节对应 `/goal` 指令；三个会话独立管理目标。
3. 先审阅 M0 的真实来源限制、周期映射和契约提议，再放行有影响的变更；不要求来源全部可用才允许其他组件推进。
4. 内容由 AI 整理，你逐条批准；发布再单独操作。每个目标关卡至少主方案、完整审核替代变体和无匹配案例。
5. 真实档案只在你的本机，且保护流程可用后由你主动提供并确认；不发给后端或其他会话作共享样例。
6. 审阅三份交接报告和分支差异；需要联调时让组件消费明确版本的服务/产物，避免复制未提交源码。
7. 完整本机和邀请服务验收满足后，再决定后续整合；本轮没有合并主分支的步骤。

## 10. 停止条件与恢复

遇到错误仓库/分支、私有数据可能外发、不可确认装备身份、证据失效、未知schema、来源授权/许可不明或契约矛盾时，停止受影响操作并报告。对不依赖该阻塞的本线程工作可继续推进。

需要暂停时在该会话发送 `/goal pause`；恢复前查看工作区与远端状态，再 `/goal resume`。保留已提交工作，不用删除目录、清理未跟踪文件或强制重置来恢复环境。

参考：[OpenAI Goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)、[独立工作目录与并行分支说明](https://learn.chatgpt.com/docs/environments/git-worktrees)。本次实际采用三个独立克隆目录，不依赖同一工作目录切分支。
